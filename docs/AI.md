术语：**provider** 指模型服务方；**工具（tool）** 指暴露给模型的、映射到既有服务层函数的一段能力；**预览卡** 指写操作在落库前给用户的确认卡片；**会话** 指 `chat_conversations` 一行及其消息。

## 1. 能力架构

四个部件，单向依赖，每一层都能单独测：

```
        ┌─────────────── 前端 ───────────────┐
        │  聊天页 (AI-05)   小窗 AI 模式 (AI-06) │
        └───────────────┬───────────────────┘
                        │ invoke  chat:send / chat:confirm
                        │ listen  chat:delta / chat:tool / chat:done / chat:error
        ┌───────────────▼───────────────────┐
        │  聊天循环（Rust，async）             │  多轮工具调用、流式转发、上下文预算
        └───────┬───────────────────┬───────┘
                │                   │
        ┌───────▼───────┐   ┌───────▼────────────┐
        │  provider 客户端 │   │  工具执行层          │
        │  OpenAI 兼容    │   │  读工具 / 写工具预览  │
        └───────┬───────┘   └───────┬────────────┘
                │                   │ 短命持锁，绝不跨网络等待
                │           ┌───────▼────────────┐
                │           │  services.rs（既有）  │
                │           └───────┬────────────┘
                │           ┌───────▼────────────┐
                │           │  repositories / SQLite │
                └──────────►│  聊天表 + llm.json 配置 │
```

三条不可动摇的边界：

1. **网络请求只在 Rust 里发。** CSP 是 `connect-src 'self' ipc: http://ipc.localhost`（[ARCHITECTURE §4.3](./ARCHITECTURE.md)），WebView 发不出外部请求——这是特性不是限制：凭据、提示词、请求体都不进页面，CSP 与 `index.html` 一个字都不用改。
2. **AI 没有自己的写路径。** 工具执行层调用 `services.rs` 里已有的函数，因此既有校验（列一致性、父任务规则、软阻塞）对 AI 同样生效。AI 不是特权调用方。
3. **持连接锁期间绝不发网络请求。** 全进程共用一条 SQLite 连接（`db::Db = Arc<Mutex<Connection>>`），一次 10 秒的模型调用若在锁内，整个应用冻结。工具执行是「锁-查-放」，网络等待在锁外（见 [§3.4](./AI.md)）。

## 2. 方案取舍

### 2.1 工具调用 vs 结构化抽取

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 工具调用（function calling）** | 定义工具集，模型自己决定调哪个、按什么顺序调，多轮循环至给出回答 | 「建任务」与「问进度」共用一套机制；模型能组合（先查项目 id 再建任务）；加能力只加一个工具定义 | 强依赖模型的工具调用质量；弱模型经常不调或调错参数，**必须有兜底** |
| **B. 结构化意图抽取** | 模型返回固定 JSON（`{intent, params}`），后端分派表执行 | 可预测、对弱模型友好、一次往返、易测 | 答不了「上周完成了哪些」，做不到「把第三条改到明天」（需要先查再改） |
| **C. 反射/Macro 生成工具 schema** | 从 `services.rs` 自动导出工具定义 | 省下几十行手写 schema | 省的是几十行，换来一套没人看得懂的宏，且会绕过「哪些能力允许暴露」这个**必须逐个决定**的问题 |

**采用 A，B 作为兜底路径。** A 与 B 共用同一个执行层（都走 `services.rs`、都过参数校验），所以不是两套实现——B 是「只有一轮、且只有一个工具」的特例。降级触发条件：未配置 provider、模型不返回工具调用、或工具调用连续两轮无法解析。

否决 C 的理由：这一层唯一真正需要人类判断的地方就是「暴露哪些能力」，把这一步自动化等于把最重要的决定交给宏。

### 2.2 读工具只返回聚合

`task:list` 一次带走整棵树（[DECISIONS §1.2](./DECISIONS.md)），对模型是灾难：70k 行既过不了上下文窗口也过不了钱包。**读工具一律返回聚合与 Top-N**（计数、进度、最近 N 条），这恰好也是「询问项目进度/最近事项」本来就需要的形状。

### 2.3 配置与凭据不进数据库

备份是整库副本、不过滤软删、导入整体替换（ADR 15），所以任何写进 `settings` 表的 API Key 都会**跟着用户导出的 JSON 备份流出去**。凭据与模型配置因此放在 app config dir 下独立的 `llm.json`：零迁移、备份天然免疫。

取舍：代价是配置不随备份迁移（换机器要重填一次）、也不随备份恢复被覆盖（这点其实是优点）。否决的备选：存 `settings` 表（会泄漏进备份）；只认环境变量（对桌面应用用户不友好，且打包后设不进去）；系统钥匙串（Tauri 2 无内置 API，要引 `keyring` 之类的依赖，超出当前需要）。

## 3. 详细设计

### 3.1 配置与凭据

配置文件：`<app config dir>/llm.json`（由 `app.path().app_config_dir()` 决定，目录不存在则创建）。

```json
{
  "baseUrl": "https://api.deepseek.com/v1",
  "apiKey": "",
  "model": "deepseek-chat",
  "temperature": 0.2,
  "maxToolRounds": 6
}
```

规则：

- **`llm:getConfig` 永不返回 `apiKey` 原文**，只返回 `hasApiKey: boolean`。前端只需要知道「已配置/未配置」。
- `baseUrl` 为空视为**未配置**，此时聊天入口给出引导而不是报错（见 [§3.3](./AI.md) 的降级路径）。
- 本地模型就是 `http://127.0.0.1:11434/v1` + 空 key，无分支。
- 配置写入走临时文件 + 重命名，避免半截文件（与 `backup` 同一习惯）。
- 打包后的报错信息里**不得回显 key**，`llm:testConnection` 的失败原因只保留状态码与服务端消息。

### 3.2 提示词与时间

系统提示是**拼出来的**，不是写死的常量，每次请求都带上：

- 当前本地时间与星期，ISO-8601 带时区偏移，例如 `2026-09-21 15:04（星期一，UTC+08:00）`；
- 可用工具清单与调用纪律（写操作会生成预览，不代表已执行）；
- 「本应用是本地单用户桌面工具」这一事实，避免模型自作主张讨论同步与协作。

**相对时间一律由模型换算成绝对时间，后端不猜。** 模型拿到当前时刻后把「明天下午三点」换算成 `2026-09-22T15:00:00+08:00`；后端只做一件事：把这个字符串解析成 UTC 并按既有规则校验，解析失败即报错回给模型重试。这与快速输入解析器的「绝不猜测，只剥离已解析内容」（ADR 16）是同一条纪律的两个面。

### 3.3 工具面

七个工具，刻意最小。每个工具都注明它映射到的既有函数。

**读工具（返回聚合与 Top-N，不返回全量）**

| 工具 | 参数 | 映射 |
| --- | --- | --- |
| `list_projects` | 无 | `project:list` + `stats:projectProgress` |
| `list_tasks` | `projectId?`、`status?`(open/done)、`dueBefore?`、`dueAfter?`、`limit`(默认 20) | `task:list`（后端按参数过滤与截断） |
| `get_task` | `id` 或 `titleQuery` | `task:list` 单行 + `comment:list` + 依赖边 |
| `search` | `query`、`limit?` | `search:query`（FTS5） |

**写工具（不落库，只产出预览）**

| 工具 | 参数 | 映射 |
| --- | --- | --- |
| `create_task` | `title`、`projectId?`、`dueAt?`(ISO-8601)、`priority?`、`complexity?`、`tagIds?` | `task:create` |
| `update_task` | `id`、以及上述任意可改字段 | `task:update` |
| `complete_task` | `id` | `task:complete` |

**刻意不暴露的能力**：删除、归档/恢复、备份导入、批量重排、标签管理。不是没实现，是不给。加白名单项必须同时改本节与 [§3.4](./AI.md)。

**降级路径**：

1. 未配置 provider → 聊天页与 AI 模式给出引导卡片（去设置里填 baseUrl/model/key），本地解析器照常工作；
2. 模型不返回工具调用 → 期望它直接回答；若用户消息明显是建任务意图，回落一次结构化抽取；
3. 网络失败、超时、401/429 → 作为一条错误气泡显示，附「重试」按钮；**不自动重试**（避免把用户的额度烧在循环里）；
4. 工具参数校验失败 → 把错误作为工具结果回给模型，让它自己改（最多 `maxToolRounds` 轮）。

### 3.4 安全模型：写操作走预览卡

**写工具绝不直接落库。** 模型调用 `create_task` / `update_task` / `complete_task` 时，后端只做三件事：

1. 参数经既有校验（只读校验，不写）；
2. 生成一张**预览**（新任务详情，或改动字段的 before/after diff），带一个随机 `previewId`，暂存在内存里（每会话最多 20 条、10 分钟过期，超出即丢弃）；
3. 把预览作为 `chat:tool` 推出的卡片，模型收到「已生成预览，等待用户确认」这个工具结果。

用户在前端点「执行」→ `chat:confirm(previewId)` → 后端用**存储的已验证参数**执行真正的服务层调用，并返回真实的实体 id。用户点「取消」→ 丢弃，一字不写。

这样做的三个后果，都是想要的：

- 模型误判不会真写数据；
- **不需要从自然语言里判断用户是否同意**——「好的」「嗯」「可以」这类解析是可靠的 bug 来源，确定性必须来自按钮而不是语言；
- 落库路径就是现有那条乐观更新 + 后端校验的路径，没有第二条写路径。

另外两条边界：执行**绝不在锁内**（锁-查-放，网络等待在锁外）；工具执行失败不得污染 store（既有 `patchRollback` 语义照旧）。

### 3.5 聊天循环与上下文预算

一次 `chat:send` 在后端做的事：写用户消息 → 组装请求 → 流式收 → 若有工具调用则执行并再发一轮 → 直到给出回答或触顶 `maxToolRounds` → 落库助手消息。

上下文预算规则（第一版，字符近似，**不引 tokenizer**）：

- 请求携带最近 N 轮完整消息（含工具调用与结果）；
- 更早的轮次压成一行文本摘要（角色 + 首行内容）；
- 单条工具结果超限即截断：保留头尾，中间以 `…（省略 N 字符）…` 标注；
- 总预算按字符数设上限，逼近时先丢最旧的历史、再截断工具结果，**系统提示与最近三条消息永不丢**。

### 3.6 数据层（V11）

```sql
CREATE TABLE chat_conversations (
    id         TEXT PRIMARY KEY,
    title      TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    deleted_at TEXT
);

CREATE TABLE chat_messages (
    id              TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL REFERENCES chat_conversations(id) ON DELETE CASCADE,
    role            TEXT NOT NULL,   -- user | assistant | tool
    content         TEXT NOT NULL,
    tool_calls      TEXT,            -- JSON 数组，助手发起的调用
    tool_call_id    TEXT,            -- role = tool 时对应的调用 id
    created_at      TEXT NOT NULL,
    deleted_at      TEXT
);
```

- 沿用既有约定：TEXT UUID 主键、ISO-8601 UTC 时间戳、`deleted_at` 软删。
- `tool_calls` 存 JSON 文本，**不建关系表**：工具调用是「消息的一部分」，独立成表只会多一张表与第二条写路径。
- 备份（`backup:export` / `backup:import`）的表清单必须加入这两张表，且文档要写明**聊天记录会进备份**；`llm.json` 不在其中。

### 3.7 命令与事件面

命令（`#[tauri::command(rename = "...")]`，注册进 `lib.rs`；前端字符串常量照习惯集中写进 `src/common/ipc/commands.ts`，见 [ARCHITECTURE §3.2](./ARCHITECTURE.md)）：

| 命令 | 说明 |
| --- | --- |
| `llm:getConfig` / `llm:setConfig` / `llm:testConnection` | 配置读写；`getConfig` 不回 key；`testConnection` 发一条最小请求做自检 |
| `chat:conversations` / `chat:history` / `chat:delete` | 会话列表、单会话消息、软删会话 |
| `chat:send` | 一条用户消息，**async + `spawn_blocking`**（照 `backup:*` 的写法） |
| `chat:confirm` | 执行预览卡里的写操作 |

事件（`emit_to(label, ...)` 定向发送，因此两个窗口可同时观察同一会话）：

| 事件 | 载荷 |
| --- | --- |
| `chat:delta` | `{ conversationId, messageId, text }` 增量文本 |
| `chat:tool` | `{ conversationId, name, status, preview? }` 工具状态与预览卡 |
| `chat:done` | `{ conversationId, messageId }` |
| `chat:error` | `{ conversationId, message }` 人类可读的失败原因 |

### 3.8 快速输入小窗的 AI 模式

小窗（`shortcut.rs` 用 `WebviewWindowBuilder` 建，session 常驻、默认隐藏）保持极简形态：

- 默认：一句话录入，完全走既有本地解析器（`quick-add-parse.ts`），**零回归、零网络**；
- `Shift+Tab`：切到 AI 模式，`set_size` 把窗口长高到能装下几轮对话，Esc 或再按 `Shift+Tab` 切回录入模式；
- 两个窗口读同一份 `chat_messages`，会话是连续的，但**渲染器与流监听器只有一份**（前端共用同一个 store 与事件订阅），不做两套。

定位差异写清楚，避免以后被当成重复功能：**聊天页是「慢慢聊」（历史、多轮、可回看），小窗是「问一句就走」（快捷键唤出、拿到答案或预览卡即关）**。同一个会话表、同一个后端循环，只有尺寸与入口不同。

`core:window:allow-set-size` 已含在 `core:default` 内（[capabilities/default.json](../src-tauri/capabilities/default.json)），**capabilities 不需要新增条目**。

### 3.9 前端形态

- 新路由 `/assistant`（TanStack Router，`lazyRouteComponent`，与既有视图同写法），侧边栏导航加一项；沿用现有设计 Token 与 Kobalte 原语，不引新 UI 依赖。
- 消息渲染：普通文本用既有排版；预览卡复用现有任务行的展示组件；工具状态是一行可折叠的注记。
- 流式渲染直接追加 DOM，不逐字重排整个列表。

### 3.10 测试

- 提示词组装的表驱动单测：当前时间注入、工具清单、相对时间换算的边界；
- **工具循环用假响应跑通**：provider 客户端的传输层可注入（等价于 `repositories` 用内存 SQLite 而不是 mock 库），因此「模型调工具 → 执行 → 再答」的整条链路**不联网也能测**；
- 执行层单测：读工具的聚合与截断、写工具只产出预览不落库、`chat:confirm` 才写、取消后库里一字未增；
- 前端单测：预览卡确认/取消、流式 delta 累加、错误气泡；
- 手工验收：真实 provider 走一遍建任务、问进度、取消预览、小窗 `Shift+Tab`。

## 4. 已识别但未定的需求

### 4.1 外部通道：周期总结与提醒（AI-07）

**需求**：通过聊天工具（Telegram / 飞书 / Slack / 钉钉等）周期性给用户发工作总结与任务提醒。

**开放问题（决策未定）**：Ordo 是纯桌面应用，**只有窗口或托盘进程活着时才有代码在跑**（现有提醒调度器就是 `scheduler.rs` 里一个 30 秒轮询的 OS 线程）。「应用没开时也要有人发消息」与这个形状直接冲突。四条候选路径，各有明确代价：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. 启动时补发 | 到点没发就攒着，下次启动/连接时补发并标注实际发送时间 | 零新增架构，与提醒去重标记（ADR 12）同一套写法；机器一直关机就永远收不到，发送时刻不精确 |
| B. 只在应用运行时准点发 | 复用 `scheduler.rs` 线程加一条定时任务 | 实现最简单；用户会误以为它像服务端一样可靠 |
| C. 常驻/独立进程 | 后台服务负责定时 | 语义最正确；要处理安装、开机自启、单实例互斥、三平台后台服务，且与「本地优先、体积小」冲突 |
| D. 外部定时器触发 CLI | 提供 `ordo-cli digest`，定时交给系统计划任务 | 代码量最小；用户体验是「要自己配一个计划任务」 |

**倾向**：D 或 A。理由是两者都不引入常驻进程，而 C 是本项目里最大的一块架构工作、收益却只是「准时」。**决定权留给「要不要做后端应用」这个更上层的问题**——用户已明确：等有后端服务时再考虑。

**实现时要连带回答的问题**（现在不答）：通道适配层怎么设计（一家一个协议，还是只做一个通用 webhook 覆盖全部——后者便宜得多）；消息投递失败与去重标记；发送内容与措辞由模型生成还是由既定模板拼；总结覆盖的时间窗口与口径（与 `stats` 的口径要对齐）。

### 4.2 多用户与任务指派（AI-08）

**需求**：接入多用户，用户之间可直接分配任务。用户明确：**暂不实现，也不预留数据结构**，只记想法。

**现状**：应用里根本没有「人」的概念——`comments` 表（V2）只有 `task_id` 与 `body`，没有作者列；计时、提醒同样都是单人隐式自己。数据模型为同步预留的是 UUID + 时间戳 + 软删（ADR 6），仅此而已。

**想清楚了的判断**（将来真做时直接可用，不必重新推导）：

1. **身份（身份与显示名）与同步（多端/多用户数据合并）是两件事，后者远大于前者。** 「显示负责人」「按人筛选」只要一个可空外键 + 一张 `persons` 表；「互相分配任务」需要同步、冲突解决、权限与可见性。前者几小时，后者是一个项目。
2. **单人应用现在加 `assignee_id` 只是在给一个恒为 null 的列写迁移**，界面上它永远只有一个可选值。等到真要做同步时再加：一条 `ALTER TABLE` + 一条 `INSERT`（把现有数据归给「我」），成本与现在相同。
3. **唯一现在就该守的纪律**：任何「谁」一律用 id 引用、显示名可改，不在业务表里硬编码人名。这条纪律是免费的语言习惯，今天写新代码时遵守即可，不需要任何结构。
4. **指派必然牵出收件箱**：「分配给我」「我分配的」「已完成待确认」是三个不同的集合，不是给任务加一个字段就能算出来的。这块的需求现在完全没有定，属于同步项目的范围。

## 5. 交付方式：分阶段与验收判据

每阶段独立可验收、可停可续，且每一阶段结束时应用都处在可用状态。

| 阶段 | 内容 | 验收判据 |
| --- | --- | --- |
| **P1** | LLM 接入层：配置读写、OpenAI 兼容 provider（含流式）、可注入传输层、提示词组装 | 配置能存能读且 key 不回前端；连通性自检成功与失败两条路都给出人话；**不联网也能跑通工具循环测试** |
